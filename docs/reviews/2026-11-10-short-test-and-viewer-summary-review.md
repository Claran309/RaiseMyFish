## 1. 能否投入使用

**可以在监护下继续使用原有直播回复功能；不建议现在批准三通道＋新侧写全部无人值守。**

短测证明关键旧问题有所改善，值得从“修框架”转入“受控日常使用＋质量验收”。但新功能又引入了数据投影与归属问题，短测也没有覆盖全部三通道：

| 范围 | 当前建议 | 原因 |
|---|---|---|
| 主人直播间、有限时段回复 | 可以监护试用 | 已有成功认人、正确房间和低延迟样例；发送正文归一化/审计一致性修复见R01 |
| 评论/私信自动常驻 | 暂不整体批准 | 当前报告主要是直播；日志中的私信分页失败与unknown需核对恢复结果，不能以直播通过替代 |
| 新侧写、档案总结 | 先试运行，修R02/R03后再长期自动运行 | 三份派生资料的撤回、失败补偿不闭环；新worker没有本次执行记录 |
| 长期无人值守与阶段完成 | 证据不足 | 缺新版本侧写实跑、三通道异常/重启验证、长期运行与真实质量对照 |

“可以用”与“全部验收完成”不是同一个结论。不要求为了试用先做大重构；先修本文有限的确定问题，再扩大运行范围。

## 2. 短测试实际证明了什么

### 2.1 明确的改善

报告里的公开样例显示：

- 问“弓长三益是谁”不再直接说陌生，而能引用过去互动。
- 问“X奇迹与你X是谁”不再回答成鱼自己。
- 问当前房间能回答主人所在房间，没有继续套旧主播房间。
- 招呼、玩笑和主动弹幕能产生正常短回复。
- 相应日志有memory_search、viewer_search调用记录，证明部分样例进入了工具执行链；检索结果是否支持最终回答，还需核对返回证据与回复归属。

日志中5次直播ReAct完成耗时为959、1182、2503、2811、777 ms，约0.78—2.81秒；这是ReAct执行阶段，不含全部排队、前置读取和平台显示。报告中有的in→out间隔约7—8秒，不能把模型耗时等同完整体验延迟。

X奇迹与你X样例用了“她”，没有足够来源证明性别时应改用“这位/你”。这不是已证明性别事实错误，但属于可以减少的无证据修饰。“Claran309这儿啊”更多是表达自然度问题，可说“主人的直播间”，不需要为它再造身份架构。

### 2.2 报告中的“全通过”应缩小范围

- out里显示文本`@Claran309`不能单独证明平台高亮/通知。当前账本正文与实际wire text还有R01差异，需真实界面观察或平台结构化证据。
- 两次认人答对不证明多人插话、同音歧义、长期纠正和普通熟人都达标；“魔”玩笑自然也不代表整个梗库质量通过。
- 这是一组短时直播样例，不是评论、私信、重启恢复或2小时退出标准的验收。
- 报告称“观众侧写版本”，但当日日志没有`viewer_summary`启动/完成事件。无法据此证明新worker或这份短测二进制已包含新侧写，更不能将答对认人归因于侧写。

## 3. 优先修复的工程问题

### R01 · P1 · 去掉文本@的时机在持久化之后

位置：[live.Send/Resume](../../internal/sender/live/live.go#L91)、[计划保存](../../internal/database/send.go#L156)、[out审计](../../internal/database/send.go#L292)。

新修复先Prepare保存`@昵称 正文`及SHA，再在内存Attempt里剥掉文本@，实际POST/Verify收到`正文`。结算重新读取持久计划，out/记忆仍保存原带@文本；防重指纹也按原文本。

离线探针实际观测：

```text
persisted plan = "@弓长三益 收到"
transport text = "收到"
structured target = 123
```

没有发现Node再次剥离，不是“双重剥前缀”。新尝试的Open与Verify都用剥后文本，不能据此直接宣布发生重复发送。确认问题是不可变计划、实际正文、审计和防重存在两套表示；旧已arm尝试升级后也没有规范化版本。

**改法**：先生成规范wire text＋结构化target，再原子持久化；Open、Verify、out和SHA使用同一快照。展示@可单独作为字段。旧计划按创建版本和原attempt处理，不能对已arm记录临时改写。

**效果/验收**：发送与记忆一致，防重口径一致，核验可重建；测试Prepare/Open/Verify/out全文一致、target持久化，以及旧unknown/已发送升级。

### R02 · P1 · 来源删除或改密后，三份侧写仍可公开使用

位置：[档案重建](../../internal/database/viewers.go#L312)、[SaveProfileSummary](../../internal/database/viewers.go#L194)、[summary保存](../../internal/viewer/summary.go#L195)。

正常输入经过ViewerRecent的SQL公开/非DM过滤，这个保障有效，不能说“私信直接被拿去侧写”。问题出在生成后：重建清理原文/向量却保留profile_summary；稳定ID的viewer_profile记忆和viewers.md也没有来源撤回传播。LLM计算期间源变更，没有提交时源版本检查。

**本轮真实PG探针**：先用两条公开事件生成侧写，再删除全部引用来源、保留其他公开事件让档案仍达门槛，重建后`profile_summary_present=true`、记忆summary仍在且`archived=false`。未操作业务public表，未证明生产已泄露。

**改法**：来源ID＋版本/hash＋生成器版本；撤回/改密时先使派生结果不可见，再异步清理三份投影和向量；保存时CAS验证源未变。知识投影保留可映射的来源，不只写一段“非人工审核”。

**效果/验收**：用户删除、纠正、改密能真正生效；公开→改密/删除/清洗、计算中撤回、档案不再达标等场景下，档案/记忆/RAG/外发embedding都没有旧资料。

### R03 · P1/P2 · 降级与知识写失败被当成最终完成

位置：[summarizeOne](../../internal/viewer/summary.go#L183)、[ActiveViewers](../../internal/database/viewers.go#L160)。

先事务保存档案/记忆并推进summary_updated_at，再写viewers.md。后者失败会报错，但无新发言时下轮不再被选中。模型timeout/坏JSON降为统计时也推进相同完成时间，已有好侧写可能被统计覆盖；模型恢复后无新发言不会重试。

两种行为均有stateful fake离线复现：知识恢复后Candidates=0/Knowledge=0；模型恢复后总调用仍为1。

**改法**：分开source_version、last_success、fallback/failed、next_retry与每个投影的dirty状态。DB事务记录待发布任务，知识失败只补投影、不重新付费；已有好版本在临时故障时保留，首次无摘要才显示统计兜底，安排有上限退避。

**效果/验收**：三份资料最终一致，临时故障不永久降低能力；测试文件故障恢复、模型恢复、进程重启、无新发言补偿、旧好版本保留，检查模型调用次数有界。

## 4. 新侧写怎样才真正有用、少污染

### R04 · P2 · 识别“另一个观众”的主要工具没带侧写

位置：[当前speaker档案](../../cmd/fishd/context.go#L92)、[viewer_search格式](../../internal/reasoning/tools_readonly.go#L302)、[查询投影](../../internal/database/viewer_search.go#L31)。

当前说话者的ProfileSummary已可注入普通Brain/ReAct；但甲问乙是谁时，viewer_search已确定乙UID也只返回昵称、次数和少量原话。关键词/语义投影未读profile_summary，格式化也丢弃它。离线给候选现有“偏好天文学”摘要，工具输出仍只有UID/昵称/统计。

**改法**：识别完成后按确定UID补取目标GetProfile，返回自动侧写、summary_updated_at与依据；甲/乙分别标识。歧义候选不强认。不要把模型侧写塞入identity向量来补接线，保持身份与内容分层。

**效果**：新功能能用于真正的“认出那个老观众”，而不是只改善当前发言者的后台片段。精确UID/昵称/确认别名解析到同UID后应取得同一份目标摘要。

### R05 · P2 · 推断被写成观众本人断言

位置：[summaryMemoryRecord](../../internal/viewer/summary.go#L369)、[档案注入](../../cmd/fishd/generate.go#L100)。

性格、关系等由LLM推断，但AssertedByID/Name被写成观众本人，置信度统一0.6；普通档案只标“-侧写”，不显示自动推断、时间。knowledge说明已有“自动生成、非人工审核”，不应说所有路径都没标记。

**改法**：subject=观众，derived_by=模型/规则，asserted_by只用于明确自述。每字段保留证据与类型（自述/观察/推断），表达“近期观察，仅参考”。实际关系和事实以来源/本人纠正为准。

**效果**：鱼可以熟悉人而不武断贴标签。优先说“最近常聊猫”，少说“你就是一个某某性格的人”。引用、反讽、一次性梗、转述他人不能自动变成本人稳定偏好。

### R06 · P2 · 最近20条是近期观察，不是完整长期侧写

目前五字段每轮重新从最近20条生成，已有侧写不进入输入，也没有稳定事实与近期话题的分层合并。一次刷屏或短时情绪可能覆盖长期偏好；关系字段仅看单方发言及次数，缺少真正配对互动。

建议分成两层：稳定的明确自述/已确认偏好，和有期限的近期话题/互动观察。更新按新证据修订而非每轮重写全部；只在新消息量、话题变化或过期时触发。给统计量和覆盖时间，不能把2句发言概括为完整性格。

不建议直接把全部弹幕塞进模型：先按UID/时间/话题选代表片段并去刷屏，跨消息保留必要上下文，避免把否定或引用截断在80字之外。三份投影只保留一个权威版本，重复命中按source/version去重，不能因为同一摘要在档案、记忆、知识出现三次就提高可信度。

## 5. 开关、成本与运维还需补齐

### R07 · P2 · 新任务与冻结/停用语义不一致

[startViewerSummary](../../cmd/fishd/viewer_summary.go#L112)只看interval，默认3600秒且**启动立即跑**，不检查Memory.Enabled、Viewer.Enabled或记忆冻结状态。关闭旧提炼/冻结记忆不一定停止新侧写写库和写知识。

若是独立任务，提供独立enabled/frozen并说明；若属于memory/viewer，就遵循其停用契约。显式interval=0能停调度，但不会清理已有摘要，不能把“任务已关”理解为“旧侧写已不使用”。

### R08 · P2 · 缺少运行面板与按投影统计

当前新任务只有日志，没有专门API/页面显示运行、最后成功、失败、fallback、来源数量、pending知识发布。部分失败时runViewerSummary直接只记录错误，返回的成功统计未展示；SSE字段白名单也不完整。

按AGENTS同步面板/API、httptest和页面断言。建议提供最近一次summary预览、来源链接、更新时间、生成类型、撤回/重建入口；不要只加“已启用”灯。普通日志仍不落全文和私密资料。

### R09 · P2 · 首次回填、预算和任务优先级需可控

ActiveViewers实际是“近期活跃 **或** hits达到门槛”，并非只处理最近24小时的人；单轮默认100人、20条、512输出token，已经有上限，但没有专门日预算/初次回填开关/共享容量门控，已有历史档案会触发一批额外调用。

建议先少量熟人试跑，分批回填；以新发言量和有效变化决定是否更新。后台优先级低于被点名回复，按成本和P95延迟调节。不要为了写总结让在线回复排队。

当前后台/embedding用量sink、purpose/correlation、cache计数与日报unknown已有实质接线；不再重复旧“完全漏账”结论。但多处适配尚未提交，在线embedding关联多为memory/viewer/knowledge而非具体event，仍需明确统计范围。缓存token计数存在不等于已验证计费折扣，也不能据这次12次调用宣称更省。

## 6. 旧问题改善与尚未证实的边界

- 凭据脚本已去字面key；本轮未验证轮换或Git历史清理，不宣称已完成。
- 目标化纠正、公开事实跨源修订、统一实际ReAct预算、unknown预占token、knowledge向量协议、旧计划路由和context释放都有新实现；尤其旧N13失败探针本轮转PASS。
- knowledge主要索引协议已修，但语义命中未携源hash与当前热快照核对，同ID更新到刷新前还有旧语义匹配新正文短窗口。可作为后续一致性增强，不据此要求停掉所有直播使用。
- 长期纠正目前仍以本轮可见资料处理，不等于DB/Soul/各派生侧写的永久撤回闭环；新侧写应纳入统一来源治理。
- 本次短测比旧版“只记得主人/旧主播”的表现好，不能把当前版本继续说成完全不会认人。也不能从少数成功样例推断跨天、多人、多通道均已达标。

## 7. 投入使用的具体路径

1. **先固定受审版本**：提交并独立验收当前用量/索引适配，记录二进制、配置、人格、数据库迁移和知识/侧写版本。不要只写“观众侧写版本”。
2. **直播继续监护试用**：解决R01后观察真实@显示、out正文、重复核验。保留快速停止、错误/unknown列表，不扩无关副作用。
3. **侧写限定小批**：先处理R02/R03；若暂未处理，停自动循环并明确哪些已有摘要仍注入/召回。试跑至少一轮成功、一轮LLM失败、一轮知识写失败，以及来源撤回。
4. **补目标观众接线和推断标记**：让甲问乙时能看到乙的有依据侧写；已知事实优先于推断，少做性格定性。
5. **私信/评论单独验收**：查明这次5条unknown和分页警告，确认后续补齐；再做同人跨通道接续、不同接收账号隔离、重启和限流。不要未经核对重投unknown。
6. **日常运行再放大**：连续观察、跨重启与后台周期后保存质量/延迟/成本数据；全部模式无人值守以正式退出门槛为准。

建议最小质量集约20组而非再无限扩方案：两个熟人各问“我是谁”、甲问乙、简称与错别字、引述/否定、不同话题插话、本人纠正侧写、旧偏好变更、短期情绪、不相关未知人、源撤回、无新话题保持安静。保存期望证据而非强制唯一措辞。

真正让项目“更好用”的优先级是：**能解释/修正自己记住的东西、每条总结有依据与时效、真实目标人物资料能进入回复、临时故障能恢复、用户能看懂运行状态。** 比继续增加梗条目或更多固定人格规则更值得优先投入。
