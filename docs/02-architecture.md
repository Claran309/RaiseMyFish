┌─────────────────────────────────────────────────────────┐

           │ Event                        │ Reply

## 2. 模块职责与依赖方向

依赖方向：**上层依赖下层接口，下层不知道上层**。

| 模块 | 职责 | 不做什么 | 依赖 |
|---|---|---|---|
| `collector` | 轮询/长连拉消息 → 标准化 Event → 入总线 | 不调 LLM、不拼 prompt | event、channel client |
| `event` | 事件结构、幂等、状态机、总线读写 | 不包含业务规则 | store |
| `scheduler` | 规则决策：回不回、何时回、用哪个 brain | 不拼 prompt、不发送 | event、memory（读状态）、brain 接口 |
| `memory` | 原始事件、提炼记录、召回、版本化 | 不做决策 | store |
| `brain` | 组装上下文 → 调 LLM/外部 agent → 返回 Reply | 不做发送、不做调度 | memory、persona、llm client |
| `sender` | 发送 → 核验 → 记账 → 回写事件 | 不做决策 | channel client、event、store |
| `persona` | 人设包加载、注入、回归测试 | 不做别的事 | 文件 |
| `store` | repository 接口 + PG 实现 | 不写业务逻辑 | GORM/pgx |
| `config` | 配置加载与校验 | 不热加载业务 | — |

## 3. 进程模型（单机多进程 / 单进程内多 goroutine）

P0 采用**单进程 `fishd` + 多个 goroutine**：

```
cmd/fishd
├─ collector goroutines（每通道一个，可配置开关）
├─ scheduler goroutine（消费事件，产出任务）
├─ brain worker pool（并发处理任务，同一会话串行）
├─ sender goroutines（每通道一个）
└─ observability（日志/日报/心跳）
```

后续可按需拆进程（同机）：
- `fishd-collect` / `fishd-core` / `fishd-send`，通过 PG 事件表协调（**不引入 MQ**）
- 拆进程是「隔离与重启便利」，不是分布式

## 4. 数据流（一条弹幕的完整生命周期）

```
1. collector: 弹幕到达 → 标准化 Event → INSERT events（幂等键去重）→ 发内存通知
2. scheduler: 收到事件 → 查规则（冷却/频控/优先级）→ 通过则创建 Task
3. brain: 组装上下文（人格包 + 召回记忆 + 共享状态 + 本事件）→ 调 LLM → Reply
4. sender: 发送弹幕 → 核验（查回执/回读）→ 记账 → 标记事件 handled
5. memory: 写 memory_event；异步 worker 判断是否提炼为 memory_record
6. observability: 记录日志、更新日报、检查心跳
```

## 5. 技术选型理由（摘要）

| 选择 | 理由 |
|---|---|
| Go 1.25+ | 并发模型适配事件驱动；单二进制；用户熟悉 |
| PostgreSQL 17+ + GORM（pgx 驱动） | 事件+任务+记忆+版本化一个库；GORM 主用，幂等/状态机/锁用 Raw SQL |
| zap | 与主人既有项目一致；结构化 JSON（纯码风，零成本） |
| 不用 Redis/MQ | 单机、低量、进程内 channel 足够；复杂度是敌人 |
| 不用分布式 | 单账号单机，天然单点；拆进程即可满足隔离 |
| 内部 interface + 对外 MCP | 解耦靠接口，MCP 管生态 |

**按需再引入（不提前锁）**：
- WS 库（QQ 通道，P3 选型）
- eino（多步工具编排，按需，见 ADR-0016）

参考资料：`docs/reference-projects.md`（三个既有项目的**码风**参考，选型按本项目需求判断）。

## 6. 关键边界（实现时必须遵守）

1. handler/scheduler 不直接碰 SQL，走 `store` 接口
2. 具体实现不跨包 import，`cmd/fishd` 统一装配
3. 事件消费先查幂等
4. 发送走「投递→确认→记账」
5. 私密/公开隔离在查询层（memory/store 层过滤）
6. 不做提前抽象：Phase 0 不写 Phase 2 的空实现

## 7. 故障模型与恢复

| 故障 | 恢复 |
|---|---|
| 采集长连断开 | 指数退避重连；从最后事件 id 补拉 |
| 进程崩溃 | 重启后从 events 表恢复未处理事件（status=pending） |
| LLM 超时/失败 | 任务重试（幂等）；超限进死信表 |
| 发送失败/核验不通过 | 进重试队列；三次失败进死信，日志告警 |
| 数据库不可用 | 进程健康检查失败 → 退出并告警（避免静默失败） |
| QQ 协议端掉线 | 降级：QQ 通道挂起，其他通道继续；恢复后补拉 |
