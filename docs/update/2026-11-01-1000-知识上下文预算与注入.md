# Change Note: 知识上下文预算与注入

## 1. What Changed

Brain现在接受可选ContextInput.Knowledge，校验后将知识放入user.context资料段。知识预算默认10%、最大10%，仍受总预算余量限制；默认调用方不传Knowledge，功能关闭，不读目录。

这次只完成K0-5接口、预算和审计；没有接生产Reader、配置开关或真实模型评测。人格、原指令、默认配置与旧评估证据保持。

## 2. Why This Change Was Needed

K0-1~4已经能召回知识，但“候选知识”不能无条件塞进模型。Brain需要检查范围，并在完整人格和记忆之后分配空间，防止知识挤掉人格、跨私密会话或因转义开销超预算。

主人本轮将原契约0–15%的上限收紧到0–10%，因此先同步契约和活动计划，再实现。0%与未启用不同：0%仍须验证上下文和保留完整人格。

## 3. Files Changed

- internal/brain/types.go：可选Knowledge输入、KnowledgeBudgetPercent默认10。
- internal/brain/context.go：知识参与输入校验/资源限制；保持nil旧路径，启用时禁止裁人格。

- internal/database/knowledge_brain_integration_test.go：假HTTP与真实PG账本组合验证。
- contracts/knowledge.md、contracts/brain.md、docs/knowledge.md及计划：统一≤10%的当前约束，DSH后续维护状态。

## 4. Core Flow After The Change

```text
合法Task/Event/Memory/Shared + 可选Knowledge
  -> 共用资源限制 + Scope/Revision/私密校验
  -> 完整人格/场景/事件优先，按原规则裁记忆
  -> K_cap计算，整条选择知识
  -> 最终实际JSON增量/总预算复核
  -> 原Provider调用 -> 原PG用量 -> 回复及安全预算审计
```

Knowledge=nil直接沿用原消息和裁剪行为，没有加载器或文件I/O。

## 5. Key Code Concepts

**余量而非抢占。** K_cap=min(floor(B*p/100),max(0,B-P-M))。前一项限制知识比例，后一项限制剩余空间，取较小值；记忆占满预算时知识为0，不把记忆再裁掉给知识腾位置。

**实际序列化成本。** 中文、引号、换行、尖括号的JSON编码开销不同。预算包括知识键、数组、分隔与ID/Source/Text，最后用实际render重新校验，不用原文长度冒充最终增量。

**同形空容器。** nil会编码成null，空slice可能编码成[]。P使用与最终记忆相同的空容器形态，M才是准确的记忆增量，避免多算/少算几个字节。

**私密范围是代码约束。** Knowledge与Event的Channel/Session/Private必须相同，私密条目Origin也必须同目标；公开内容仍须符合场景。prompt里写“别泄露”不能代替这些校验。

## 6. Important Implementation Details

完整人格P超过B时，非nilKnowledge直接返回budget，即使没有召回或比例0；nil路径仍保留原P0裁人格行为。知识只整条保留，长条放不下可以试短条，不切半句接法。

为避免反复重编码整段大prompt，每个条目只编码一次计算增量，最后再render核对。输入受4096项/4MiB总限额保护，循环检查取消；排序/裁剪用副本，不污染Reader或调用方快照。

审计只记录允许范围内的ID、Revision和开销，正文不进日志/Meta。知识不进system或instructions，且资料经JSON HTML转义；这保护段结构，不宣称彻底解决模型提示注入。重试、超时、未知费用NULL及实际调用才记账的规则保持。
