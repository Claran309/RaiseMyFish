# Change Note: 知识装配诊断与离线检索验证

## 1. What Changed

fishd现在能按配置构造knowledge.Reader，`fishd check`输出PG和装配状态，知识默认关闭、预算上限10%。只完成装配与诊断，没有事件worker或生产调用链路接入。

另新增100条离线检索验证，相关率46/56=82.14%、私密越界0；但正例43/60低于48/60，因此K0-7全部质量门槛尚未通过。没有跑真实模型开/关各35条。

## 2. Why This Change Was Needed

K0-5提供了知识DTO和预算能力，仍需要可信入口读取文件并告诉操作者“是关闭、已加载还是加载失败”。加载成功不等于知识已被模型消费，因此诊断明确输出pipeline_connected=false。

质量不能用“返回过三条”证明。新验证将命中、无命中、权限反例和预算分开检查，发现只靠标题/标签的当前Reader对没有标题词面的自然场景覆盖不足。

## 3. Files Changed

- internal/config/knowledge.go、config.go及测试：enabled/dir/budget_percent默认值、0–10限制与严格配置校验，配置层不读目录。
- cmd/fishd/knowledge.go、main.go、brain.go及测试：FileReader装配、安全错误链、check诊断及Brain比例传递；保留原check-brain。
- internal/knowledge/snapshot.go及测试：只读SnapshotInfo Revision/Entries，不改变Recall匹配或排序。
- config/fishd.toml：显式新增关闭的knowledge段，不打开默认配置。
- internal/knowledgeeval/与cmd/knowledgeeval/：独立离线评测器、100条冻结标注及合成权限/排序fixture，不改人格评测器。
- 新K0-6/K0-7报告、契约/手册和本人交接：保护旧证据、保留一次运行与质量失败。

## 4. Core Flow After The Change

```text
Config.Load/Validate -> PG ready
  -> 可选Brain构造（不Reply）
  -> Knowledge关闭：不碰目录
     Knowledge启用：NewFileReader -> 不可变快照元信息
  -> fishd check JSON（模型0调用、用量0、生产链路未连接）
```

离线检索使用另一条独立路径：先冻结查询/答案/源文件/代码，再用相同原字节临时副本构造Reader，运行100条，输出逐条ID及相关率/覆盖/权限/预算结果。

## 5. Key Code Concepts

**装配不等于链路。** 知识Reader和Brain可以已构造，但尚无调度worker把召回结果交给实际事件。诊断只说明快照成功加载，不宣称生产知识生效。

**元信息来自同一快照。** SnapshotInfo只读Reader内部不可变版本与计数；删除临时源文件后仍能读取同样元信息，不二次扫库或靠路径/mtime猜版本。

**相关率与覆盖率不同。** 46条相关返回除以56条实际返回得到82.14%，但有17个应命中的正例完全没返回预期，因此覆盖43/60不达48。不能只报好看的一个指标。

**权限需要对照。** 发布库全是公开条目，空结果不能证明私密隔离。独立合成私密Origin及QQ场景fixture用相同查询、不同合法Scope做镜像，证明资料确实可召回，但错误会话/平台/公开目标拿不到。

## 6. Important Implementation Details

配置关闭时不访问目录，启用失败明确报错，不把坏文件当零命中；安全错误隐藏目录/正文，Unwrap保留取消等原因。check不获取服务单例锁、不写status、不调用Brain.Reply或LLM账本。

K0-7为60正例/20无命中/20权限反例；精确标题20、带标题自然句20、无标题语义场景20，发布库keywords为空，所以不伪称测了alias能力。预期ID由开发者预先审读，不等于DSH独立标注。合法镜像与排序控制不抬高相关率分母。

Top3固定顺序10次通过；100条都使用真实Brain和内存fake验证JSON增量≤10%，合成人格并非生产人格效果对照。实际私密fixture全为合成数据，不含用户私信。首次质量运行后未改查询/预期/源库/Reader，覆盖不足如实保留。
