# Phase 3 · QQ 接入

> 目标：让 QQ 里的鱼和 B站 的鱼是同一条（共享人格与记忆）。
> 两个方案二选一，先做验证再定。

## 依赖

Phase 1（多通道架构验证）、Phase 2（记忆共享）。

## 方案选择（决策点）

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 自写 OneBot 客户端（`pkg/onebot`） | 架构统一、收发可控、无 Python | 需处理 WS 重连/协议细节 |
| B. AstrBot HTTP API 转发 | 省事、有 WebUI | Python 异构；收消息需插件转发 |

**倾向 A**；B 作为兜底。决策前先各花 1 天做 spike。

## 任务清单

### 3.1 协议端对接
- [ ] 协议端选型（NapCat / LLBot），记录版本与已知问题
- [ ] 登录态保持、断线重连、监控
- [ ] **协议端可替换**：客户端只依赖 OneBot v11 JSON

### 3.2 Collector（qq）
- [ ] 消息接收（私聊/群聊）
- [ ] 幂等键 `qq:{bot_id}:{msg_id}`
- [ ] 自消息过滤
- [ ] 群聊仅 @ 触发（或配置触发词）
- [ ] 私聊 = private

### 3.3 Sender（qq）
- [ ] 文本发送
- [ ] 回执核验
- [ ] 群聊 @ 规则

### 3.4 人格与记忆
- [ ] context.md 增加 qq 段（浓/淡场合）
- [ ] 回归集增加 QQ 场景
- [ ] 共享状态：QQ 与 B站 互见

### 3.5 降级
- [ ] 协议端掉线：QQ 通道挂起，B站 继续
- [ ] 恢复后补拉/补回

### 3.6 测试
- [ ] mock 协议端：收发/断线/重连
- [ ] 群聊 @ 过滤器测试
- [ ] 四通道人格一致性回归

## 退出标准

1. QQ 私聊与群聊可用，消息不重不漏
2. 协议端重启后自动恢复，不影响其他通道
3. QQ 与 B站 语气一致（回归集覆盖）
4. 协议端替换成本低（换一个协议端只需改配置）

## 风险

| 风险 | 应对 |
|---|---|
| 协议端被风控/封号 | 小号、可替换、降级告警 |
| OneBot 协议细节多 | 先实现最小集（文本+私聊+群@） |
| 群聊误触发 | 默认仅 @，不加唤醒词 |
